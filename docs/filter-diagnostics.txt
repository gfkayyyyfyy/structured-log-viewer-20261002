无效日志诊断：为什么未命中筛选条件的行仍会产生警告
==================================================

本文解释 log_viewer 的无效行诊断行为：某些行明明不满足筛选条件、不会出现在
输出里，却仍然会在标准错误产生一条“无效日志”警告。原因是判定顺序——无效性
检查发生在筛选条件（级别选择、request_id、时间区间、message 子串）之前，
一行在“是否匹配”被考虑之前就可能已被判为无效。

本文所有结论均以当前源码为依据，不修改任何产品代码。涉及文件：

- log_viewer/__main__.py   命令行入口 main()
- log_viewer/__init__.py   parse_timestamp() / normalize_level() /
  parse_line_range() / compare_decimal_strings() / iter_matches()

文中行号为当前源码行号，随源码演进可能漂移，以函数名为准。


1. 调用链：从 python -m log_viewer 到 iter_matches
--------------------------------------------------

1.1 入口与参数校验（全部在读取文件之前）

`python -m log_viewer` 执行 log_viewer/__main__.py 的 main()（第 10 行起）。
argparse 解析参数后，按固定顺序校验，任一失败即向标准错误打印“参数错误：…”
并 return 2，此时尚未打开文件，标准输出为空：

1. --jsonl 与 --summary 互斥检查            （__main__.py 第 90-92 行）
2. 每个 --level 值经 normalize_level() 规范化后
   必须属于 SUPPORTED_LEVELS                （第 96-106 行）
3. --request-id 不能为空或全空白            （第 111-116 行）
4. 每个 --message-contains 值各自校验：该选项可重复给出，任一次值
   为空字符串或全空白即参数错误（即使其他值合法）  （第 122-130 行）
5. --since 经 parse_timestamp() 解析        （第 133-141 行）
6. --until 经 parse_timestamp() 解析        （第 144-152 行）
7. --since 晚于 --until 为错误；相等是合法空区间（第 154-157 行）
8. --line-range 只能提供一次，且必须是 START:END：两端为只含 ASCII
   数字的正十进制整数（允许前导零，不接受符号或空白），端点为零或
   起点大于终点均为参数错误                        （第 164-182 行）

1.2 文件读取与物理行拆分

- 以 UTF-8、newline="" 整体读入文件（第 186-191 行）。OSError 或
  UnicodeDecodeError 打印“文件读取失败：…”并 return 2，标准输出为空。
- 仅移除文件最开头的一次 UTF-8 BOM（第 200-201 行），不占行号。
- 按 LF 拆分物理行，仅对被 LF 终止的分段去掉 CRLF 中紧邻 LF 的 CR
  （第 206-210 行）。行号从 1 开始按物理行计算。

1.3 iter_matches 的逐行判定顺序

main() 在第 211-213 行调用
iter_matches(lines, levels, request_id, since, until, message_contains)，
返回 (matches, warnings) 两个 (行号, 文本) 列表。iter_matches
（__init__.py 第 79-178 行）对每一行按以下顺序判定，任一环节 continue
即进入下一行——这是“每行最多一条警告”的结构性保证：

  a. 空白行（去除首尾空白后为空）：静默跳过，不占警告，但占行号
     （第 134-135 行）。
  b. json.loads 解析失败：警告“无效日志：JSON 解析失败”（第 136-145 行）。
  c. 顶层不是 JSON 对象：警告“无效日志：顶层不是 JSON 对象”（第 146-148 行）。
  d. level 经 normalize_level() 规范化后不属于 SUPPORTED_LEVELS：
     警告“无效日志：level 缺失或不属于支持的级别”（第 149-152 行）。
     注意此处只检查“级别是否受支持”，尚未检查“是否在所选级别内”。
  e. 仅当 --since/--until 至少给出一个时（check_time，第 121 行），
     解析顶层 timestamp，失败则警告“无效日志：timestamp 缺失或格式无效”
     （第 153-158 行）。此检查在级别选择之前，因此级别不匹配所选集合的
     记录也会因 timestamp 无效而产生警告。未启用时间筛选时完全不检查
     timestamp——字段缺失或格式非法都不会产生任何警告。
  f. 级别不在所选集合内：静默跳过，无警告（第 159-160 行）。
  g. request_id 不精确相等（含字段缺失、为 null、非字符串）：
     静默跳过，无警告（第 161-164 行）。
  h. message 不包含任一给定候选子串（可重复提供，多候选取并集；
     含字段缺失、为 null、非字符串）：静默跳过，无警告（第 165-172 行
     附近；iter_matches 也接受单个字符串，与旧调用约定兼容）。
  i. record_time < since：静默跳过（含起点，第 173-174 行）。
  j. record_time >= until：静默跳过（不含终点，第 175-176 行）。
  k. 全部通过：加入 matches（第 177 行）。

关键结论：步骤 b-e 是“无效行警告”（数据本身不合法），步骤 f-j 是“静默跳过”
（数据合法但不满足筛选条件）。警告只看数据合法性，不看是否命中筛选；
因此未命中筛选条件的行仍可能因 b-e 产生警告，而合法但未命中的行绝不产生
警告。

1.4 行号区间过滤与三种输出模式（互斥关系与格式均保持不变）

若提供了 --line-range，main() 在 iter_matches 返回之后、输出之前按原始
物理行号过滤 matches（第 218-225 行）：只保留行号落在闭区间内的匹配，
不重排、不重新编号；warnings 完全不受影响，因此区间外的无效行照常
警告，matched_count 与 by_level 只统计区间内的命中，invalid_count 仍为
全文件警告数。

main() 先把全部警告按行号顺序写到标准错误（第 226-227 行），再按模式写
标准输出，三种模式互不影响警告流：

- 默认模式（第 253-255 行）：每行匹配输出 `行号<Tab>原始行`。
- --summary（第 228-240 行）：标准输出只有一个 JSON 对象和末尾换行，
  含 matched_count、invalid_count（即警告条数）、by_level（五个级别
  各自的命中数，未命中为 0）。
- --jsonl（第 241-252 行）：每条匹配只写原始正文和一个 LF。

正常完成默认 return 0（第 256 行附近），存在无效行不影响退出码。
可选开关 --strict（store_true，无值，可重复）不改变上述任何输出与警告，
只改最终退出码：输出全部完成后，只要本次 warnings 非空即 return 1，
否则 return 0；判定仍是步骤 b-e 的既有无效行规则，--line-range 范围外
的警告同样计入，未匹配（f-j）与空白行（a）不计。--strict=true 等带值
写法由 argparse 在读取文件前以退出码 2 拒绝，标准输出为空。


2. 示例文件 demo.jsonl
----------------------

以下为本文档自带的示例文件内容（与仓库根目录既有 demo.jsonl 无关，请按
此处内容另行创建）。UTF-8 编码、LF 分隔、共六行，第一行为空白行：

（空行）
{
{"level":"TRACE"}
{"level":"INFO"}
{"level":" error ","request_id":"r-1","timestamp":"2026-10-03T10:00:00Z"}
{"level":"ERROR","request_id":"r-1","timestamp":"2026-10-03T10:01:00Z"}

可用以下命令生成（printf 的 \n 即 LF）：

  printf '\n{\n{"level":"TRACE"}\n{"level":"INFO"}\n{"level":" error ","request_id":"r-1","timestamp":"2026-10-03T10:00:00Z"}\n{"level":"ERROR","request_id":"r-1","timestamp":"2026-10-03T10:01:00Z"}\n' > demo.jsonl

逐行性质（行号从 1 开始）：

  第 1 行  空白行：占行号，静默跳过，不计为无效（判定 a）。
  第 2 行  只有一个左花括号：JSON 解析失败，无效（判定 b）。
  第 3 行  level 为 TRACE：JSON 合法但级别不受支持，无效（判定 d）。
  第 4 行  level 为 INFO：数据合法；不在所选级别内，且缺少 timestamp——
           是否产生警告取决于是否启用时间筛选（判定 e 先于 f）。
  第 5 行  level 为 " error "：规范化后为 ERROR，合法；timestamp 恰为
           区间起点（含起点）。
  第 6 行  level 为 ERROR：合法；timestamp 恰为区间终点（不含终点）。


3. 复现命令一：时间区间 + 默认输出
----------------------------------

命令（选择 ERROR 级别和请求标识 r-1，--since/--until 分别设为示例中的两个
时刻）：

  python -m log_viewer demo.jsonl --level ERROR --request-id r-1 \
      --since 2026-10-03T10:00:00Z --until 2026-10-03T10:01:00Z

3.1 预期结果（依据第 1 节的源码判定顺序推导）

标准输出（仅第五行原文，带行号和制表符前缀）：

  5	{"level":" error ","request_id":"r-1","timestamp":"2026-10-03T10:00:00Z"}

标准错误（三条警告，按行号顺序）：

  第 2 行：无效日志：JSON 解析失败
  第 3 行：无效日志：level 缺失或不属于支持的级别
  第 4 行：无效日志：timestamp 缺失或格式无效

退出码：0

3.2 逐行判定位置

  第 1 行  空白 → 静默跳过（__init__.py 第 134-135 行）。
  第 2 行  "{" 无法解析 → 警告（第 136-145 行）。
  第 3 行  TRACE 不在 SUPPORTED_LEVELS → 警告（第 149-152 行）。
  第 4 行  INFO 合法，但已启用时间筛选（check_time 为真，第 121 行），
           timestamp 缺失 → 警告（第 153-158 行）。注意：此行级别 INFO
           本就不在所选的 ERROR 内，但 timestamp 检查（判定 e）位于
           级别选择（判定 f）之前，所以“级别不匹配”不能使它免于警告。
  第 5 行  level 规范化后为 ERROR（第 149 行 normalize_level 去空白转
           大写）；timestamp 2026-10-03T10:00:00Z 解析成功；级别在所选
           集合内；request_id 精确相等；record_time >= since（含起点，
           第 173 行）且 < until（第 175 行）→ 命中（第 177 行）。
  第 6 行  全部合法，但 record_time 2026-10-03T10:01:00Z >= until
           （不含终点，第 175-176 行）→ 静默跳过，无警告。

3.3 实际执行记录（当前源码实测，与 3.1 预期一致）

  $ python3 -m log_viewer demo.jsonl --level ERROR --request-id r-1 \
        --since 2026-10-03T10:00:00Z --until 2026-10-03T10:01:00Z
  [标准输出]
  5	{"level":" error ","request_id":"r-1","timestamp":"2026-10-03T10:00:00Z"}
  [标准错误]
  第 2 行：无效日志：JSON 解析失败
  第 3 行：无效日志：level 缺失或不属于支持的级别
  第 4 行：无效日志：timestamp 缺失或格式无效
  [退出码] 0


4. 复现命令二：无时间边界 + --summary
-------------------------------------

命令（同样选择 ERROR 和 r-1，但不设 --since/--until，启用 --summary）：

  python -m log_viewer demo.jsonl --level ERROR --request-id r-1 --summary

4.1 预期结果

标准输出（一个 JSON 对象和末尾换行）：

  {"matched_count": 2, "invalid_count": 2, "by_level": {"DEBUG": 0, "INFO": 0, "WARNING": 0, "ERROR": 2, "CRITICAL": 0}}

标准错误（只有第二、三行两条警告）：

  第 2 行：无效日志：JSON 解析失败
  第 3 行：无效日志：level 缺失或不属于支持的级别

退出码：0

4.2 逐行判定位置及与命令一的差异

  未传 --since/--until 时 check_time 为假（__init__.py 第 121 行），
  判定 e 整段跳过，完全不检查 timestamp：

  第 1 行  空白 → 静默跳过（第 134-135 行）。
  第 2 行  JSON 解析失败 → 警告（第 136-145 行）。
  第 3 行  TRACE 不受支持 → 警告（第 149-152 行）。
  第 4 行  INFO 合法；不检查 timestamp（无警告）；级别不在所选集合内
           → 静默跳过（第 159-160 行）。与命令一相比，此行少一条警告，
           差异完全由是否启用时间筛选造成。
  第 5 行  命中（判定 f/g 通过，无时间区间约束）。
  第 6 行  命中（同理；无 --until，终点排除规则不生效）。

  汇总（__main__.py 第 228-240 行）：matched_count=2（第 5、6 行），
  invalid_count=2（两条警告），by_level 按命中行规范化后的 level 计数，
  ERROR 为 2，DEBUG/INFO/WARNING/CRITICAL 均为 0。

5. 为什么每个无效非空行最多一条警告
----------------------------------

iter_matches 的循环体（__init__.py 第 133-177 行）中，每一处
warnings.append(...) 之后紧跟 continue，且判定 b-e 按顺序串行执行、
互不嵌套。一行在第一个命中的无效判定处即产生警告并跳到下一行，后续的
无效判定不再执行。例如某行 JSON 可解析、level 非法且 timestamp 缺失，
只会收到“level 缺失或不属于支持的级别”一条警告，不会叠加 timestamp
警告。空白行在判定 a 即被跳过，连无效性检查都不进入，因此占行号但
永不计为无效。


6. 失败路径：退出码 2，标准输出为空
-----------------------------------

与无效行警告（退出码仍为 0）不同，以下两类失败在任何文件内容被处理前
即终止，标准输出保持为空，错误信息写标准错误，退出码为 2：

- 参数错误（__main__.py 第 90-182 行）：--jsonl 与 --summary 同用、
  --level 值为空/全空白/不受支持、--request-id 为空或全空白、
  任一 --message-contains 值为空或全空白（该选项可重复给出，
  其他值合法也不能覆盖该错误）、--since/--until 格式非法、
  --since 晚于 --until、--line-range 重复提供或格式非法（含端点
  为零、起点大于终点）。
  此外完全缺少 --level 或某次缺值由 argparse 本身以退出码 2 处理。
- 文件读取失败（第 186-191 行）：路径不存在、是目录、无权限或内容不是
  合法 UTF-8，打印“文件读取失败：<路径>（<异常>）”。

实际执行记录（当前源码实测）：

  $ python3 -m log_viewer demo.jsonl --level ERROR --since bad
  [标准输出] （空，0 字节）
  [标准错误] 参数错误：--since 必须是 YYYY-MM-DDTHH:MM:SSZ 格式的 UTC 时间
  [退出码] 2

  $ python3 -m log_viewer missing.jsonl --level ERROR
  [标准输出] （空，0 字节）
  [标准错误] 文件读取失败：missing.jsonl（[Errno 2] No such file or directory: 'missing.jsonl'）
  [退出码] 2
