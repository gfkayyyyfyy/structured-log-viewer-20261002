导出再导入说明：原文保留、物理行号与行结束符在这条路径上的实际含义
====================================================================

本文解释 log_viewer 的“--jsonl 导出 → 同一入口再次导入”流程：先用
--jsonl 把匹配记录导出为一份新的 JSONL 文件，再把它作为输入重新读取。
重点说明三件事在这条路径上的实际含义：

- 原文保留：哪些内容逐字节保留，保留发生在哪个阶段；
- 物理行号：两次运行各自的行号如何计算，为什么不相等；
- 行结束符：LF、CRLF 与单独 CR 在读取和导出时分别如何处理。

本文所有结论均以当前源码为依据，不修改任何产品代码、命令参数或公开
接口。涉及文件：

- log_viewer/__main__.py   命令行入口 main()
- log_viewer/__init__.py   iter_matches() 等

文中行号为当前源码行号，随源码演进可能漂移，以函数名为准。文中
“预期结果”由源码推导，“实际执行记录”为对当前源码的真实运行结果，
两者分别标注；本文不把再次导入描述成恢复原文件。


1. 流程总览
-----------

两次运行同一入口，中间由 shell 重定向把第一次的标准输出保存为文件：

  python -m log_viewer demo.jsonl --level ERROR --jsonl > result.jsonl
  python -m log_viewer result.jsonl --level ERROR

第一次是导出：读 demo.jsonl，筛出 ERROR 记录，每条只写原始正文和一个
LF。第二次是再导入：把 result.jsonl 当作一份全新的输入文件，按与任何
其他输入完全相同的规则读取、分行、筛选、输出。两次运行互不感知：
第二次不知道行号、BOM 或行结束符在第一次之前的形态。


2. 示例文件 demo.jsonl 的字节定义
---------------------------------

仓库根目录的 demo.jsonl 即本示例文件。按 UTF-8 字节定义为四个物理行，
文件开头只有一次 BOM（EF BB BF）：

  第 1 行  {"level":"INFO","message":"开始"}   以 LF 结束
  第 2 行  （空行）                              以 CRLF 结束
  第 3 行  not-json                             以 LF 结束
  第 4 行  {"level":"ERROR","message":"失败"}   后接一个单独 CR，
                                                文件到此结束，没有 LF

完整字节序列（xxd 输出，中文为 UTF-8 多字节）：

  00000000: efbb bf7b 226c 6576 656c 223a 2249 4e46  ...{"level":"INF
  00000010: 4f22 2c22 6d65 7373 6167 6522 3a22 e5bc  O","message":"..
  00000020: 80e5 a78b 227d 0a0d 0a6e 6f74 2d6a 736f  ...."}...not-jso
  00000030: 6e0a 7b22 6c65 7665 6c22 3a22 4552 524f  n.{"level":"ERRO
  00000040: 5222 2c22 6d65 7373 6167 6522 3a22 e5a4  R","message":"..
  00000050: b1e8 b4a5 227d 0d                        ...."}.

可用以下命令按字节精确生成（不经过文本模式，避免任何换行转换）：

  python3 - <<'EOF'
  data = (
      b'\xef\xbb\xbf'
      + '{"level":"INFO","message":"开始"}'.encode('utf-8') + b'\n'
      + b'\r\n'
      + b'not-json\n'
      + '{"level":"ERROR","message":"失败"}'.encode('utf-8') + b'\r'
  )
  with open('demo.jsonl', 'wb') as f:
      f.write(data)
  EOF


3. 第一次运行：导出
-------------------

命令：

  python -m log_viewer demo.jsonl --level ERROR --jsonl > result.jsonl

3.1 源码处理位置（__main__.py main()）

  a. 读文件（第 132-137 行）：以 encoding="utf-8"、newline="" 整体读入。
     newline="" 关闭通用换行转换，不紧邻 LF 的单独 CR 原样保留，不会在
     读取时被翻译成 LF 而拆开物理行。OSError 或 UnicodeDecodeError
     打印“文件读取失败：…”并 return 2，标准输出为空（见第 7 节）。
  b. 去除开头标记（第 146-147 行）：仅当解码后的内容以 U+FEFF 开头时
     移除这一次 BOM。它不占物理行号，也不会进入任何输出。
  c. 划分物理行（第 152-156 行）：按 LF 拆分；仅对被 LF 终止的分段
     （除最后一个外）去掉 CRLF 中紧邻 LF 的那个 CR。最后一个分段没有
     终止 LF，即使以 CR 结尾也原样保留——因此第 4 行末尾的单独 CR
     属于正文内容，不是行结束符。
  d. 逐行判定（第 157-159 行调用 iter_matches，__init__.py 第 41-118
     行）：行号由 enumerate(lines, start=1)（第 82 行）对全部物理行
     统一编号。空白行在第 83-84 行静默跳过——它不占警告、不进结果，
     但已经消耗了一个行号，所以空行仍占原行号。第 3 行 not-json 在
     第 85-89 行被判为 JSON 解析失败，进入 warnings 而非 matches，
     因此损坏行不进入导出结果，只在标准错误留下含原行号的警告。
  e. 写出结果（第 175-186 行）：--jsonl 模式只遍历 matches，对每条
     记录把原始正文 raw.encode("utf-8") 和一个 LF（b"\n"）直接写入
     sys.stdout.buffer。正文不重新序列化，不带行号和制表符前缀；
     末行即使源文件没有终止 LF 也补一个 LF。

3.2 预期结果（由 3.1 推导）

  标准输出：只有第 4 行的正文，不带原行号和 BOM；由于第 4 行末尾的
  单独 CR 是正文内容（见 c），它被原样写出，随后是导出补上的 LF，
  即 JSON 正文后依次是 CR 和 LF。

  标准错误：只有一条“第 3 行：无效日志：JSON 解析失败”。行号是 3
  而不是 2，因为第 2 行的空行仍占原行号（见 d）。

  退出码：0（存在无效行不影响退出码）。

3.3 实际执行记录（当前源码实测，与 3.2 一致）

  $ python3 -m log_viewer demo.jsonl --level ERROR --jsonl > result.jsonl
  [标准输出，保存为 result.jsonl 后的 xxd]
  00000000: 7b22 6c65 7665 6c22 3a22 4552 524f 5222  {"level":"ERROR"
  00000010: 2c22 6d65 7373 6167 6522 3a22 e5a4 b1e8  ,"message":"....
  00000020: b4a5 227d 0d0a                           .."}..
  [标准错误]
  第 3 行：无效日志：JSON 解析失败
  [退出码] 0

  可见 result.jsonl 以 JSON 正文开头（无 BOM、无行号），结尾两字节
  为 0d 0a：0d 是第 4 行正文里原有的单独 CR，0a 是导出补上的 LF。

3.4 保存 result.jsonl 时避免转码和换行转换

  产品本身把字节直接写入 sys.stdout.buffer（第 182-186 行），标准输出
  上的字节是确定的；可能改变字节的是保存环节。请使用不做文本转换的
  重定向：Linux/macOS 的 shell 和 Windows 的 cmd.exe 用 > 原样写字节；
  Windows PowerShell 5.1 的 > 会转码为 UTF-16LE，不要使用，可改用
  cmd /c 重定向或 Python 读取子进程字节后写文件。同理，不要经过任何
  会做换行转换（CRLF 归一化）的编辑器或管道保存该文件。


4. 第二次运行：再导入
---------------------

命令：

  python -m log_viewer result.jsonl --level ERROR

4.1 源码处理位置

  与第一次完全相同的一段代码（第 132-159 行），对 result.jsonl 重新
  执行：读文件、（无 BOM 可去）、按 LF 划分物理行、iter_matches 逐行
  判定。两点在本例中起决定作用：

  - 行号从 1 重新计算：enumerate(lines, start=1)（__init__.py 第 82
    行）对当前输入的物理行编号。result.jsonl 只有一行内容，所以它的
    行号是 1，与它在 demo.jsonl 中的原行号 4 无关。
  - 单独 CR 此时被当作行结束符的一部分去除：result.jsonl 中该记录
    现在是“正文 + CR + LF”，按 LF 拆分后该分段以 CR 结尾且不是最后
    一个分段（末尾还有一个空分段），于是 __main__.py 第 152-156 行
    把这个 CR 作为 CRLF 中紧邻 LF 的 CR 去掉。第一次运行时它是正文
    内容，第二次运行时它成了行结束符的一部分——同一个字节，地位
    由它是否紧邻 LF 决定。

  输出走默认模式（第 187-189 行）：print(f"{lineno}\t{raw}")，即
  行号、制表符、正文，随后是 print 补的输出换行。

4.2 预期结果（由 4.1 推导）

  标准输出：行号 1、一个制表符、该 ERROR 对象正文，随后是输出换行；
  正文末尾不再含 CR（已在分行时作为 CRLF 的一部分去除）。

  标准错误：空（result.jsonl 中唯一的行是合法 ERROR 记录）。

  退出码：0。

4.3 实际执行记录（当前源码实测，与 4.2 一致）

  $ python3 -m log_viewer result.jsonl --level ERROR
  [标准输出的 xxd]
  00000000: 3109 7b22 6c65 7665 6c22 3a22 4552 524f  1.{"level":"ERRO
  00000010: 5222 2c22 6d65 7373 6167 6522 3a22 e5a4  R","message":"..
  00000020: b1e8 b4a5 227d 0a                        ...."}.
  [标准错误] （空，0 字节）
  [退出码] 0

  可见输出为 31 09（"1" 和制表符）+ JSON 正文 + 0a，正文末尾的
  0d 已不存在。


5. 保留与变化对照
-----------------

沿这条路径，哪些内容保留、哪些因筛选和重新分行发生变化：

保留（仅针对“通过全部筛选条件的记录的正文”）：
  - 正文字节本身：不重新序列化，首尾空白、字段顺序、中文、JSON 转义
    原样保留（第 175-186 行直接写字节）。
  - 正文中不紧邻 LF 的单独 CR：读取时因 newline="" 保留（第 132-134
    行），导出时随正文写出（本例第 4 行末尾的 CR 进入了 result.jsonl）。

变化（筛选与重新分行引入，属预期行为）：
  - 未命中的行（本例第 1 行 INFO）不进入导出结果——这是筛选的目的。
  - 损坏行（本例第 3 行 not-json）不进入导出结果，只在标准错误留下
    含原行号的警告；警告文本不属于导出内容。
  - 文件开头的 BOM 在读取时被移除（第 146-147 行），不出现在导出中。
  - 行号不随导出保存：导出不含行号，再次导入时行号从 1 重新计算。
  - 行结束符被重新分行统一化：每条导出记录以一个 LF 结束（末行也补
    LF），原文件中 LF / CRLF / 无终止符的差异不保留；原正文中末尾的
    单独 CR 在再次读取时因此紧邻 LF，被当作 CRLF 行结束符的一部分
    去除，不再出现在正文中。

因此，再次导入不是恢复原文件：导出结果只是“命中记录正文的子集 +
 统一 LF 终止”，原文件的未命中行、无效行、BOM、行号和原有行结束符
形态都无法从 result.jsonl 还原。


6. 原文保留的适用阶段与限制
---------------------------

“原文保留”只适用于一个明确阶段：一条物理行被划分出来、去掉其行结束
符之后，到它作为匹配记录被导出为止。在这一阶段内，正文不被重新
序列化、不被修改，逐字节写回标准输出。

在此阶段之外不作任何保留承诺：读取前的 BOM、行结束符形态，筛选中
被丢弃的行，以及行号，都不在保留范围内。因此不能声称任意输入都能
经过导出再导入保持字节完全一致——本例本身即是反例：输入四行（含
BOM、空行、损坏行、末尾单独 CR），导出再导入后只剩一行、行号从 1
起算、末尾 CR 消失。只有在“输入只含合法且全部命中的记录、每行以
LF 或 CRLF 终止、无 BOM、正文末尾不含单独 CR”这类受限条件下，导出
内容才可能与输入的正文部分逐字节一致，本文不对该类条件之外的情形
作任何断言。


7. 失败路径：非法 UTF-8 与路径不存在
------------------------------------

本例的两次运行若遇到文件无法读取——路径不存在、是目录、无权限或
内容不是合法 UTF-8——行为与任何其他输入一致（第 132-137 行）：
标准输出为空，标准错误打印“文件读取失败：<路径>（<异常>）”，
退出码为 2。注意 BOM 的移除发生在解码成功之后（第 146 行），因此
BOM 之后若存在非法 UTF-8 字节仍按文件读取失败处理。

实际执行记录（当前源码实测）：

  $ printf '\xef\xbb\xbf{"level":"ERROR"}\n\xff\xfe\n' > bad-utf8.jsonl
  $ python3 -m log_viewer bad-utf8.jsonl --level ERROR --jsonl
  [标准输出] （空，0 字节）
  [标准错误] 文件读取失败：bad-utf8.jsonl（'utf-8' codec can't decode byte 0xff in position 21: invalid start byte）
  [退出码] 2

  $ python3 -m log_viewer missing.jsonl --level ERROR --jsonl
  [标准输出] （空，0 字节）
  [标准错误] 文件读取失败：missing.jsonl（[Errno 2] No such file or directory: 'missing.jsonl'）
  [退出码] 2

（标准错误中括号内的异常细节由操作系统和 Python 版本决定，不固定。）


8. 兼容性说明
-------------

本文仅为流程说明，不改变任何行为：main()、iter_matches() 的调用与
返回约定，--level、--request-id、--since/--until、--message-contains、
--summary、--jsonl 各参数的语义，默认/--summary/--jsonl 三种输出模式
的格式与互斥关系，无效行警告规则，以及退出码约定（正常 0、参数错误
与文件读取失败 2）均保持现状。其他筛选、摘要和警告规则不因本文所述
流程而改变。
