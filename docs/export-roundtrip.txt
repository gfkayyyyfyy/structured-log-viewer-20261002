导出再导入说明：--jsonl 路径上的原文保留、物理行号与行结束符
================================================================

本文解释查看器已有的一条使用路径：用 --jsonl 把匹配记录导出到标准输出、
重定向保存为文件，再把该文件作为输入经同一入口读取。重点说明这条路径上
“原文保留”“物理行号”“行结束符”三件事的实际含义，并给出一个可以在本地
逐字节复现的示例。

本文只交付说明与示例，不改变任何产品行为、命令参数或公开接口。文中“预期”
一节由当前源码推导，“实测记录”一节为对当前源码的真实运行结果，两者分别
标注；未执行过的内容不会写成实测。若源码日后变更，行号与运行记录请重新核对。

涉及文件：

- log_viewer/__main__.py   命令行入口 main()
- log_viewer/__init__.py   iter_matches() / normalize_level()

文中行号为撰写时的当前源码行号，随源码演进可能漂移，以函数名与代码意图为准。

环境说明：实测机只有 python3（Python 3.14.4，Linux），命令写作
`python3 -m log_viewer`；在 python 即 Python 3 的环境中等同于
`python -m log_viewer`。


0. 一句话结论
-------------

--jsonl 逐字节保留的是“命中行被去掉行结束符之后的正文”，而不是原文件。
筛选会丢弃行、开头标记会被移除、行号是每次读取时按物理行重新从 1 计算的，
导出还会给每条记录统一补一个 LF；因此再次导入是“读取一份只含命中记录的新
JSONL 文件”，不是恢复原文件，也不能保证任意输入导出再导入后字节完全一致。


1. 源码位置：读文件、去开头标记、划分物理行、写出结果
------------------------------------------------------

以下四处都在 main()（log_viewer/__main__.py）中，是本文的依据。

1.1 读文件（第 130-137 行）

    with open(args.path, "r", encoding="utf-8", newline="") as f:
        content = f.read()
    except (OSError, UnicodeDecodeError) as exc:
        print(f"文件读取失败：{args.path}（{exc}）", file=sys.stderr)
        return 2

- 按 UTF-8 整体读入为一个字符串。非法 UTF-8 抛 UnicodeDecodeError、路径
  不存在等抛 OSError：打印“文件读取失败：…”到标准错误并以退出码 2 结束，
  标准输出为空，不产出部分结果。
- newline="" 关闭 Python 的通用换行转换：读取时不把任何字符翻译成 LF，
  正文中不紧邻 LF 的单独 CR 原样保留。

1.2 去除开头一次标记（第 139-147 行）

    if content.startswith("﻿"):
        content = content[1:]

- 仅当整个文件最前面是 U+FEFF（UTF-8 字节 EF BB BF，BOM）时移除这一次。
- 移除发生在 UTF-8 解码成功之后；标记之后若有非法字节仍按读取失败处理。
- 标记不占物理行号；只移除最开头的一次，其他位置的 U+FEFF 属于正文。

1.3 划分物理行（第 149-156 行）

    parts = content.split("\n")
    lines = [
        part[:-1] if index < len(parts) - 1 and part.endswith("\r") else part
        for index, part in enumerate(parts)
    ]

物理行只由 LF 终止，规则只有两句：

- 按 LF 拆分，每个 LF 结束一个物理行，行号从 1 开始（enumerate start=1，
  在 __init__.py 第 82 行）。因此 LF 之间即使为空也占一个行号。
- 对“被 LF 终止的分段”（除最后一个分段外），若分段以 CR 结尾，仅去掉
  紧邻 LF 的那一个 CR（CRLF 的 CR）。最后一个分段没有终止 LF：即使以 CR
  结尾，该 CR 也属于正文，原样保留。

不被当作行结束符的字符（不会拆分物理行，也不会被删除）：

- 不紧邻 LF 的单独 CR（含文件末尾无 LF 时结尾的 CR）；
- 正文中的 U+2028 / U+2029 等 Unicode 字符。

1.4 筛选与警告（log_viewer/__init__.py 第 82-117 行）

iter_matches() 对 lines 从行号 1 开始逐行判定：

- 空白行（第 83-84 行，raw.strip() 为空）：静默跳过，不警告，但占行号；
- JSON 解析失败（第 85-89 行）：追加 (行号, "无效日志：JSON 解析失败")
  警告并跳过该行；
- 顶层非对象、level 缺失或不受支持（第 90-96 行）：警告并跳过；
- 级别不在所选集合（第 103-104 行）等其余筛选条件：静默跳过；
- 全部通过才 matches.append((lineno, raw))（第 117 行），raw 是未做任何
  重新序列化的原始正文。

警告随后由 main() 按行号顺序写到标准错误（__main__.py 第 160-161 行），
退出码仍为 0。

1.5 写出结果（第 162-189 行，三种互斥模式）

- --jsonl（第 175-186 行）：直接写标准输出的底层字节缓冲
  sys.stdout.buffer，每条匹配写 raw.encode("utf-8") 再写一个 b"\n"。
  正文不重新序列化，不写行号与制表符，不加外层数组或统计字段；末行即使
  源文件没有终止 LF 也补一个 LF。
- 默认逐行模式（第 187-189 行）：print(f"{lineno}\t{raw}")，即
  “当前这次读取计算出的行号 + 一个制表符 + 原始正文 + 输出换行”。
- --summary（第 162-174 行）：与本文示例无关，规则不变。


2. 示例文件 demo.jsonl 的字节定义
---------------------------------

仓库根目录的 demo.jsonl 即本示例输入，按 UTF-8 字节定义为四个物理行：

  偏移      内容                                                         说明
  0x00      EF BB BF                                                    文件开头唯一一次 BOM
  0x03 起   {"level":"INFO","message":"开始"}                           第 1 行正文（“开始”为 UTF-8 字节 E5 BC 80 E5 A7 8B）
  其后      0A                                                          LF，结束第 1 行
           0D 0A                                                       空行（0 字节正文）以 CRLF 结束，即第 2 行
           not-json                                                    第 3 行正文（损坏行）
           0A                                                          LF，结束第 3 行
           {"level":"ERROR","message":"失败"}                          第 4 行正文（“失败”为 E5 A4 B1 E8 B4 A5）
  末尾      0D                                                          一个单独 CR，文件到此结束，其后没有 LF

可用 POSIX shell 重新生成（\xHH 按字节写入，不做转码）：

  printf '\xef\xbb\xbf{"level":"INFO","message":"\xe5\xbc\x80\xe5\xa7\x8b"}\n\r\nnot-json\n{"level":"ERROR","message":"\xe5\xa4\xb1\xe8\xb4\xa5"}\r' > demo.jsonl

实测字节（xxd demo.jsonl，共 87 字节）：

  00000000: efbb bf7b 226c 6576 656c 223a 2249 4e46  ...{"level":"INF
  00000010: 4f22 2c22 6d65 7373 6167 6522 3a22 e5bc  O","message":"..
  00000020: 80e5 a78b 227d 0a0d 0a6e 6f74 2d6a 736f  ...."}...not-jso
  00000030: 6e0a 7b22 6c65 7665 6c22 3a22 4552 524f  n.{"level":"ERRO
  00000040: 5222 2c22 6d65 7373 6167 6522 3a22 e5a4  R","message":"..
  00000050: b1e8 b4a5 227d 0d                        ...."}.

第一次读取时的内部形态（BOM 移除、按 LF 拆分后）：

  parts[0] 第 1 行 = {"level":"INFO","message":"开始"}     被 LF 终止，结尾非 CR，不删字符
  parts[1] 第 2 行 = \r            → 被 LF 终止且以 CR 结尾，删掉 CR，正文为空（空行）
  parts[2] 第 3 行 = not-json                             被 LF 终止，正文即 not-json
  parts[3] 第 4 行 = {"level":"ERROR","message":"失败"}\r 最后一个分段，无终止 LF，
                                                            结尾单独 CR 属于正文，保留

第 4 行正文末尾的 CR 是 JSON 允许的空白，json.loads 可正常解析，因此它是
合法 ERROR 记录；CR 本身仍作为 raw 的一部分逐字节保留。


3. 第一次操作：导出 result.jsonl
--------------------------------

3.1 命令与保存方式

  python3 -m log_viewer demo.jsonl --level ERROR --jsonl > result.jsonl

程序向标准输出写的是 UTF-8 原始字节（见 1.5），shell 重定向 `>` 原样落盘，
不经过任何文本层。保存时必须避免转码和换行转换：

- 不要把输出先捕获进 PowerShell 变量或经 PowerShell 管道（可能按
  UTF-16/其他编码重新写出），直接用 shell 重定向；
- 不要用编辑器打开后另存（可能自动加 BOM、把 LF 改成 CRLF 或在末尾加行）；
- 保存后用 `xxd result.jsonl`（或 `od -An -tx1 result.jsonl`）逐字节核对。

3.2 预期（由第 1 节源码推导）

- 标准输出只导出第 4 行：不带行号与制表符、不带 BOM、不加任何包装；
  正文逐字节照写，随后依次是该正文保留下来的单独 CR（0D）和导出统一补的
  LF（0A）。第 1 行级别不匹配被静默过滤；第 2 行是空行；第 3 行损坏。
- 标准错误只有一条：第 3 行的“无效日志：JSON 解析失败”警告，带原行号 3。
- 退出码 0（存在无效行不影响退出码）。

3.3 实测记录（当前源码实测，与 3.2 一致；共 38 字节）

  $ python3 -m log_viewer demo.jsonl --level ERROR --jsonl > result.jsonl
  [退出码] 0
  [result.jsonl 字节，xxd]
  00000000: 7b22 6c65 7665 6c22 3a22 4552 524f 5222  {"level":"ERROR"
  00000010: 2c22 6d65 7373 6167 6522 3a22 e5a4 b1e8  ,"message":"....
  00000020: b4a5 227d 0d0a                           .."}..
  [标准错误]
  第 3 行：无效日志：JSON 解析失败

即正文 36 字节 + 0D + 0A。结尾两个字节是 0D 0A：0D 是第 4 行作为“末行无
LF”时保留在正文里的 CR，0A 是 --jsonl 为每条记录补的 LF。这只是“一个 CR
后面恰好跟着补写的 LF”，第一次读取时它是正文，不是行结束符。


4. 这一步保留了什么、改变了什么
--------------------------------

保留（仅限“命中行去掉行结束符之后的正文”，且只到写出为止）：

- 正文的每个 UTF-8 字节：首尾空白、字段顺序、中文、JSON 转义形式均不重新
  序列化（__main__.py 第 183-184 行直接 encode 原始字符串）；
- 正文内部不紧邻 LF 的单独 CR（本例第 4 行末尾 CR 即如此保留）、U+2028/
  U+2029 等字符；
- 多条命中时的原文件行序。

发生变化（不保留原文件形态）：

- 行结束符：读入时 LF 以及 CRLF 中紧邻 LF 的 CR 已按 1.3 去除，不会被导出；
- 统一重写终止符：每条导出记录末尾固定补一个 LF（0A），与源行原来用 LF、
  CRLF 还是无终止 LF 无关；本例源文件末尾是“CR 且无 LF”，result.jsonl
  末尾变为 0D 0A；
- 开头 BOM：只在源文件最前面存在一次，读取时已移除，导出文件没有 BOM；
- 筛选：级别不匹配行（第 1 行）、空行（第 2 行）、损坏行（第 3 行）都不进入
  result.jsonl；警告只写标准错误；
- 行号：不导出，也没有任何形式记录；下次读取时重新计算（见第 5、6 节）。


5. 第二次操作：再次读取 result.jsonl
------------------------------------

5.1 命令

  python3 -m log_viewer result.jsonl --level ERROR

5.2 预期（由第 1 节源码推导）

result.jsonl 现在的字节是“ERROR 正文 + 0D + 0A”。再次读取时：

- 按 LF 拆分得到两个分段：parts[0] 为“ERROR 正文 + CR”（被这个 LF 终止），
  parts[1] 为空的最后分段（终止 LF 之后的尾部分段，物理行号为 2，是空白行，
  静默跳过、不警告）；
- parts[0] 被 LF 终止且以 CR 结尾（1.3 的条件成立）：这一次 CR 被当作
  CRLF 行结束符的一部分删除。它在第一次读取时属于“末行正文”，在第二次
  读取时属于“CRLF 的 CR”，字符没变，归属变了；
- ERROR 记录命中。默认模式输出“当前这次读取的行号 1 + 一个制表符 +
  不含 CR 的正文 + print 的输出换行（LF）”，标准错误为空，退出码 0。

5.3 实测记录（当前源码实测，与 5.2 一致；标准输出共 39 字节）

  $ python3 -m log_viewer result.jsonl --level ERROR
  [标准输出字节，xxd]
  00000000: 3109 7b22 6c65 7665 6c22 3a22 4552 524f  1.{"level":"ERRO
  00000010: 5222 2c22 6d65 7373 6167 6522 3a22 e5a4  R","message":"..
  00000020: b1e8 b4a5 227d 0a                        ...."}.
  [标准错误] （空，0 字节）
  [退出码] 0

逐字节看：31 09 是“1”和制表符；正文与 demo.jsonl 第 4 行正文相同；
最后只有 0A，5.2 中被删除的 CR（0D）不再出现。


6. 四个“为什么”
----------------

6.1 为什么空行仍占原行号

物理行号在筛选之前由 content.split("\n") 的分段位置决定（__main__.py
第 152-156 行），iter_matches 拿到 lines 后只是对第几个分段就报几
（__init__.py 第 82 行 enumerate start=1）。空行是一个长度为 0 的真实分段，
所以第 2 行这个号被它占用；它在第 83-84 行被静默跳过，不产生警告、不进入
结果，但后面的 not-json 仍顺延为第 3 行——这正是警告显示“第 3 行”的原因。

6.2 为什么损坏行不进入导出结果

导出写出的集合是 iter_matches 的 matches，而 not-json 在 json.loads 处失败
（__init__.py 第 85-89 行），只追加警告并 continue，从不执行第 117 行的
matches.append。因此第 3 行既不出现在标准输出，也不会出现在 result.jsonl；
它存在的唯一痕迹是标准错误里带原始行号 3 的警告。

6.3 为什么再次读取行号从 1 重新计算

行号不是文件内容的一部分，--jsonl 也不导出它。每次运行 main() 都重新执行
“读文件 → split → enumerate(start=1)”，行号描述的是“本次输入文件的第几个
物理行分段”。result.jsonl 里只有一条记录（其后跟一个终止 LF），这条记录
自然是第 1 行；demo.jsonl 中的“第 4 行”这一身份不会被带过来。因此本示例中
同一条 ERROR 记录，第一次显示行号 4，再读取显示行号 1。

6.4 为什么单独 CR 在第二次读取时被当作行结束符的一部分去除

1.3 的判定完全依赖“分段后面有没有 LF”，与 CR 的来历无关：

- 第一次读取：第 4 行是最后一个分段，后面没有 LF（条件 index < len(parts)-1
  不成立），结尾 CR 原样保留为正文并被导出；
- 导出在它后面补了一个 LF（__main__.py 第 185 行）；
- 第二次读取：同一段字节变成“被 LF 终止且以 CR 结尾”的分段，条件成立，
  紧邻 LF 的那个 CR 按 CRLF 规则删除（__main__.py 第 154 行）。

同一个 0D，第一次是正文，第二次是行结束符的一部分——这是两次读取的文件
形态不同造成的，不是同一次处理中规则不一致。

6.5 为什么不能把再次导入描述成“恢复原文件”

对比 demo.jsonl（87 字节）与两次输出即可看到差异：

- BOM 没了（EF BB BF 只在第一次读取的开头被移除，不进入 result.jsonl）；
- 第 1 行 INFO、第 2 行空行、第 3 行 not-json 都被筛选掉，文件从四个物理行
  变为一条记录；
- 第 4 行的行号由 4 变为 1，行结束形态由“末尾 CR、无 LF”变为“CRLF”，再次
  默认输出时正文末尾连 CR 都不再出现。

“原文保留”的适用阶段仅限于：单次读取内，从正文拆分完成（1.3）到该命中行被
写出（1.5）之间，raw 这段字符不被重新序列化、其字节不被改动。它不覆盖
读取时的行结束符剥离、开头标记移除、筛选丢弃、导出统一补 LF，也不延续到
下一次读取。因此不能声称任意输入经过导出再导入都能保持字节完全一致；本例
恰好展示了一个被保留一次、随后在第二次读取时消失的 CR。


7. 失败路径补充（实测）
-----------------------

本例之外，输入为非法 UTF-8 或路径不存在时，在任何行被处理之前即终止：
标准输出为空（0 字节），标准错误报告“文件读取失败：<路径>（<原因>）”，
退出码 2。--jsonl 模式实测如下（当前源码，Python 3.14.4 / Linux）：

  $ printf '{"level":"ERROR"}\n\xff\n' > bad-utf8.jsonl
  $ python3 -m log_viewer bad-utf8.jsonl --level ERROR --jsonl
  [标准输出] （空，0 字节）
  [标准错误] 文件读取失败：bad-utf8.jsonl（'utf-8' codec can't decode byte 0xff in position 18: invalid start byte）
  [退出码] 2

  $ python3 -m log_viewer no-such-file.jsonl --level ERROR --jsonl
  [标准输出] （空，0 字节）
  [标准错误] 文件读取失败：no-such-file.jsonl（[Errno 2] No such file or directory: 'no-such-file.jsonl'）
  [退出码] 2

稳定可依赖的是退出码 2、标准输出为空、标准错误以“文件读取失败：”开头并含
路径；括号内异常文案随 Python 版本与语言环境可能不同。BOM 在解码成功后才
移除，所以“BOM 之后存在非法 UTF-8”同样走这条路径，不会输出部分结果。


8. 其余规则保持现状
-------------------

除本文描述的既有行为外，其他筛选、摘要和警告规则一律不变，包括：
--level 多值相等匹配与规范化、--request-id 精确相等、--since/--until 的
含起点/不含终点时间区间与 timestamp 警告、--message-contains 子串匹配、
--summary 的 matched_count/invalid_count/by_level 输出、无效行每行最多一条
警告且不影响退出码、参数错误在读取文件前以退出码 2 拒绝、默认逐行输出格式
为“行号<Tab>原始行”。
